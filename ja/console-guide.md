## Compute > Instance > コンソール使用ガイド { #compute-instance-console-guide }

<a id="create-instances"></a>
## インスタンスの作成 { #create-instances }

下の設定を使用してインスタンスを作成するか、インスタンステンプレート (Instance Template) を使用してインスタンスを作成できます。インスタンステンプレートからインスタンスを作成するには、インスタンス作成画面で **[インスタンステンプレートを使用]** を選択します。インスタンステンプレートの作成方法については、「[インスタンステンプレート コンソール使用ガイド](/Compute/Instance%20Template/ja/console-guide/)」を参照してください。

![インスタンス作成ガイド表紙](../static/images/image-1704.jpg)

<a id="os-settings"></a>
### OS 設定 { #os-settings }

インスタンス作成時に使用するルート ブロックストレージの作成方式を決定します。

- **新規作成および設定** または **既存リソース指定** のいずれかを選択します。
- **新規作成および設定** を選択した場合、イメージを使用してルート ブロックストレージを作成します。
- **既存リソース指定** を選択した場合、既存のブロックストレージまたはスナップショットを使用します。

<a id="image"></a>
### イメージ { #image }

目的のオペレーティング システムがインストールされたイメージを選択します。イメージは、NHN Cloud から提供されるパブリック イメージ、既に作成したユーザー イメージ、または共有イメージから選択できます。

使用するイメージに応じてインスタンス タイプ (flavor) が異なるため、インスタンス作成時は最初にイメージを選択してから進めます。

| オペレーティング システム              | ブロックストレージ | メモリ    |
| --------------------------------- | ------------- | --------- |
| Linux<br>Ubuntu、Debian、Rocky    | 20GB 以上     | 1GB 以上  |
| Windows                           | 50GB 以上     | 2GB 以上  |

<a id="root-block-storage"></a>
### ルート ブロックストレージ { #root-block-storage }

**OS 設定** に従ってルート ブロックストレージを設定します。

- **新規作成および設定** を選択した場合、**ブロックストレージ タイプ** と **ブロックストレージ サイズ** を指定してルート ブロックストレージを作成します。
- **既存リソース指定** を選択した場合、**元のリソース** を指定してルート ブロックストレージとして使用します。

<a id="root-block-storage-original-resource"></a>
#### 元のリソース

既存の **ブロックストレージ** または **スナップショット** のいずれかを選択できます。

- **ブロックストレージ** を選択した場合、既存のブロックストレージをルート ブロックストレージとして使用します。
- **スナップショット** を選択した場合、既存のスナップショットを使用してルート ブロックストレージを作成します。

<a id="root-block-storage-block-storage-size"></a>
#### ブロックストレージ サイズ

インスタンスのルート ブロックストレージ サイズを決定します。

- ブロックストレージ サイズは、イメージが必要とする最小サイズ以上である必要があります。

インスタンスのルート ブロックストレージ サイズは、インスタンス タイプによって異なります。

| タイプ                    | サポート対象のブロックストレージ サイズ |
| ----------------------- | -------------------------------- |
| u2 タイプ               | 20〜100 GB (タイプごとに固定)    |
| t2、m2、c2、r2、x1 タイプ | 20〜2000GB                      |

> [注記]
> ブロックストレージ サイズに応じて料金が発生するため、ルート ブロックストレージのサイズを無条件に大きくするのは非効率です。必要に応じてブロックストレージを追加して使用することをお勧めします。
> **OS 設定** で **既存リソース指定** を **ブロックストレージ** で選択した場合、ブロックストレージ サイズの変更はできません。
> **OS 設定** で **既存リソース指定** を **スナップショット** で選択した場合、ブロックストレージ サイズは元のブロックストレージ サイズ以上に設定する必要があります。

<a id="root-block-storage-block-storage-type"></a>
#### ブロックストレージ タイプ

インスタンスのルート ブロックストレージ タイプを決定します。

- **HDD** または **SSD** のいずれかを選択します。タイプによって料金とパフォーマンスが異なります。
- 一度選択したブロックストレージ タイプは変更できません。

> [注記]
> **OS 設定** で **既存リソース指定** を選択した場合、ブロックストレージ タイプの変更はできません。

<a id="availability-zone"></a>
### Availability Zone { #availability-zone }

可用性ゾーンを明示的に設定しない場合、任意のゾーンに設定されます。可用性ゾーンに応じて、このインスタンスが使用できるブロックストレージが決定されます。使用するブロックストレージが特定の可用性ゾーンに存在する場合は、その可用性ゾーンを設定して使用します。

> [注記]
> VPC のリソースはすべての可用性ゾーンで使用できます。
> **OS 設定** で **既存リソース指定** を選択した場合、可用性ゾーンは変更できません。

可用性ゾーンの詳細については、「[インスタンス概要の可用性ゾーン](./overview/#availability-zone)」を参照してください。

<a id="flavor"></a>
### タイプ (flavor) { #flavor }

仮想ハードウェアのパフォーマンスに応じて、さまざまなタイプから選択できます。ただし、イメージが必要とする仮想ハードウェアのパフォーマンスに応じて、選択できるタイプが制限される場合があります。詳細については、「[インスタンス概要](./overview)」を参照してください。

> [注記]
> 1 vCPU は、スレッド 1 つとコア 1 つで構成されたソケット 1 つを意味します。ソケット 1 つあたりのスレッド数とコア数はそれぞれ 1 つで一定です。

インスタンスのタイプは、作成後も NHN Cloud コンソールで変更できます。上位のタイプから下位のタイプに変更することも、下位のタイプから上位のタイプに変更することもできます。一部のタイプは変更できない場合もあるため、詳細については「[インスタンス タイプの変更](./console-guide/#modify-flavor)」を参照してください。

> [注意]
> インスタンスのルート ブロックストレージはタイプ変更で置き換えることはできません。

<a id="number-of-instances"></a>
### インスタンス数 { #number-of-instances }

イメージ、可用性ゾーン、タイプ、ブロックストレージ サイズ、キー ペア、ネットワーク設定がすべて同じインスタンスを複数作成する場合に使用します。インスタンス名には、設定した名前の後に `-1`、`-2` のような番号が付けられて作成されます。たとえば、インスタンス名を `my-instance` として 2 つのインスタンスを作成すると、`my-instance-1` と `my-instance-2` が作成されます。一度に作成できるインスタンスの最大数は 10 個です。

任意の可用性ゾーンに複数のインスタンスを作成した場合、各インスタンスは任意の可用性ゾーンに作成されます。たとえば、2 つのインスタンスを任意の可用性ゾーンで作成した場合、2 つが同じ可用性ゾーンに作成される場合もあれば、異なる可用性ゾーンに作成される場合もあります。すべてのインスタンスが同じ可用性ゾーンに作成される必要がある場合は、特定の可用性ゾーンを選択して作成します。

> [注記]
> **OS 設定** で **既存リソース指定** を **ブロックストレージ** で選択した場合、または **ネットワーク設定** で **既存ネットワーク インターフェイス指定** を選択した場合、インスタンス数は `1` に制限されます。

<a id="key-pair"></a>
### キー ペア { #key-pair }

既存のキー ペアを使用するか、新しいキー ペアを生成して使用します。既存のキー ペアの登録については、Windows ユーザーの場合は「[キー ペアのインポート (Windows ユーザー)](./console-guide/#import-key-pairs-windows)」を、Mac と Linux ユーザーの場合は「[キー ペアのインポート (Mac、Linux ユーザー)](./console-guide/#import-key-pairs-mac-and-linux)」を参照してください。

> [注記]
> キー ペアはユーザー アカウントに割り当てられたリソースであるため、プロジェクトを削除してもキー ペアは削除されず、保持されます。

<a id="network"></a>
### ネットワーク { #network }

VPC で定義されたサブネットから、インスタンスに接続するサブネットを選択します。1 つのサブネットを選択するたびに、インスタンスにそのサブネットに接続するネットワーク インターフェイスが作成されます。選択したサブネットの順序を変更してネットワーク インターフェイスを変更することもできます。この場合、最初のネットワーク インターフェイス (`eth0`) がデフォルト ゲートウェイとして設定されます。

ネットワークの作成と管理の詳細については、「[VPC 概要](/Network/VPC/ja/overview/)」を参照してください。

<a id="floating-ip"></a>
### フローティング IP { #floating-ip }

インスタンス作成後、フローティング IP の使用有無を指定します。フローティング IP の使用を選択すると、新しいフローティング IP を生成して、最初のネットワーク インターフェイスに接続します。この場合、最初のネットワーク インターフェイスは、必ずインターネット ゲートウェイが設定されたサブネットに接続されている必要があります。

フローティング IP の管理は、インスタンス > 管理ページまたはインスタンス > フローティング IP ページでも実行できます。フローティング IP の詳細については、「[VPC コンソール使用ガイド](/Network/VPC/ja/console-guide/)」を参照してください。

<a id="security-group"></a>
### セキュリティ グループ { #security-group }

インスタンスが属するセキュリティ グループを指定します。1 つのインスタンスは複数のセキュリティ グループに属することができます。インスタンスが複数のセキュリティ グループに属する場合は、以下の点に注意してください。

- 各セキュリティ グループに属するすべてのインスタンスとネットワーク通信が可能です。他のインスタンスからの予期しないアクセスをブロックする必要がある機密データを保持するインスタンスの場合は、セキュリティ グループを慎重に指定してください。
- 各セキュリティ グループのすべてのルールが組み合わされて、そのインスタンスの外部通信に適用されます。

セキュリティ グループの詳細については、「[VPC コンソール使用ガイド](/Network/VPC/ja/console-guide/)」を参照してください。

<a id="additional-block-storage"></a>
### 追加ブロックストレージ { #additional-block-storage }

インスタンス作成後、追加ブロックストレージの接続有無を指定します。追加ブロックストレージの使用を選択した場合、ルート ブロックストレージとは別の新しいブロックストレージを作成してインスタンスに接続します。ルート ブロックストレージと同様に、追加ブロックストレージを作成するときに名前、ストレージ タイプ、サイズを指定できます。

ルート ブロックストレージは OS 用にのみ使用し、よく使用するアプリケーションまたはデータを追加ブロックストレージに保管すると、ブロックストレージの接続/切断またはスナップショット機能を使用して、簡単に転送または複製できます。また、インスタンスに障害が発生した場合、追加ブロックストレージのみを切断してから別のインスタンスに接続して、サービスを簡単に復旧できます。

ブロックストレージの管理はインスタンス > ブロックストレージ ページでも実行できます。ブロックストレージの詳細については、「[ブロック ストレージ ガイド](/Storage/Block%20Storage/ja/overview/)」を参照してください。

<a id="placement-policy"></a>
### 配置ポリシー { #placement-policy }

配置ポリシーを使用してインスタンスを異なるハイパーバイザーに配置できます。インスタンス作成時に配置ポリシーを設定すると、同じ配置ポリシーに割り当てられたインスタンスは異なるハイパーバイザーに作成されます。

> [注意]
> 分散配置ができない状況の場合、インスタンス作成に失敗する可能性があります。

<a id="user-script"></a>
### ユーザー スクリプト { #user-script }

インスタンス作成後に実行するスクリプトを指定します。ユーザー スクリプトは、インスタンスの最初のブート完了後、ネットワーク設定などの初期化処理が完了した後に実行されます。NHN Cloud のユーザー スクリプトは、公式イメージに組み込まれた cloud-init (Linux)、Cloudbase-init (Windows) などの自動化ツールによって実行されます。

> [注意]
> ユーザー スクリプトは root (Linux)/Administrator (Windows) ユーザー権限で実行されます。

<a id="user-script-linux"></a>
#### Linux

ユーザー スクリプトの最初の行は必ず `#!` で始まる必要があります。
```
#!/bin/bash
...
```

ユーザー スクリプトが正常に動作するには、インスタンス内のログ ファイルを確認する必要があります。スクリプトから標準出力/エラー デバイスに出力されたログは `/var/log/cloud-init-output.log` で確認できます。

<a id="user-script-windows"></a>
#### Windows

Windows イメージでは、ユーザー スクリプト形式として Batch スクリプト形式と PowerShell スクリプト形式の両方をサポートしています。各形式は、最初の行に指定されたディレクティブによって区別されます。

* Batch スクリプト
```
rem cmd
...
```

* PowerShell スクリプト
```
#ps1_sysnative
...
```

Batch スクリプトと PowerShell スクリプトを一緒に使用する場合は、次のように記述します。

* EC2 形式
```
<script>
...
</script>
<powershell>
...
</powershell>
```

ユーザー スクリプトのログは `C:\Program Files\Cloudbase Solutions\Cloudbase-Init\log\cloudbase-init` で確認できます。

ユーザー スクリプトの詳細については、「[cloud-init](https://cloudinit.readthedocs.io/en/latest/topics/format.html)」または「[Cloudbase-init](https://cloudbase-init.readthedocs.io/en/latest/userdata.html)」ガイドを参照してください。

<a id="change-instance-status"></a>
### インスタンス状態変更 { #change-instance-status }

インスタンスの停止、終了、削除、および起動を通じてインスタンスの状態を変更することができます。

インスタンスの停止、終了、削除のハイパーバイザーリソースおよび料金関連情報は、以下の表を参照してください。

| 区分 | インスタンス停止 | インスタンス終了 | インスタンス削除 |
| --- | -- | --- | --- |
| ハイパーバイザーリソース | リソース割り当て状態を維持 | リソース返納およびインスタンス起動時に再割り当て | リソース削除 |
| インスタンス料金 | 停止料金ポリシーを適用 | 無料 | 無料 |
| 関連する他のリソース料金 | 課金される | 課金される | 課金される |

> [注記] GPU インスタンスは終了することはできず、停止時にも正常(100%) 料金が発生します。

<a id="create-image"></a>
### イメージ生成 { #create-image }

インスタンスのルートブロックストレージからイメージを生成します。イメージ生成はデータ一貫性を保証するため、インスタンスを停止した状態で実行することをお勧めします。

インスタンスのルートブロックストレージに空き領域がまったくない場合、イメージ生成は可能ですが、イメージを別のインスタンスで使用するための初期化作業はできないため、正常に使用できません。イメージを生成する前に、インスタンスで最小100KB の空き領域を確保する必要があります。

生成されたイメージは **Compute > Image** に Private イメージとして登録されます。登録されたイメージを使用して、元のインスタンスと同じブロックストレージを持つインスタンスを生成できます。

> [注意]
> 生成されたイメージのサイズは、ルートブロックストレージの実際の使用量より大きくなる可能性があります。

<a id="associatedisassociate-floating-ip"></a>
### フローティング IP の関連付けと解除 { #associatedisassociate-floating-ip }

インスタンスの状態に関係なく、フローティング IP を関連付けたり、解除したりできます。使用可能なフローティング IP がない場合、または目的のフローティング IP がない場合は、**[作成]** ボタンをクリックしてフローティング IP を生成して関連付けることができます。または **Network > VPC > Floating IP** でフローティング IP を生成して使用することもできます。

フローティング IP の詳細については、[VPC 概要](/Network/VPC/ja/overview/) を参照してください。

<a id="modify-security-group"></a>
### セキュリティグループの変更 { #modify-security-group }

インスタンスの状態に関係なく、インスタンスのセキュリティグループを変更できます。変更されたセキュリティグループはすぐに適用されます。

セキュリティグループの詳細については、[セキュリティグループ](./console-guide/#security-group) および [VPC 概要](/Network/VPC/ja/overview/) を参照してください。

<a id="change-network-subnet"></a>
### ネットワークサブネットの変更 { #change-network-subnet }

インスタンスのネットワークサブネットは、インスタンスが停止している状態でのみ変更できます。サブネットを追加すると、インスタンスにそのサブネットに接続されるネットワークインターフェイスが自動的に作成されます。この場合、一度に複数のサブネットを追加すると、インスタンスに新規に作成されるネットワークインターフェイスの順序は任意で指定されます。インスタンスからサブネットを削除すると、作成されたネットワークインターフェイスも自動的に削除されます。

<a id="modify-flavor"></a>
### インスタンスタイプの変更 { #modify-flavor }

インスタンスタイプは、インスタンスを停止してから変更できます。インスタンスが実行中の場合は、**[追加機能]** の **[インスタンス停止]** をクリックしてインスタンスを停止します。

現在のタイプに応じて、変更できるインスタンスタイプが異なります。

* m2、c2、r2、t2、x1 タイプのインスタンスは、m2、c2、r2、t2、x1 タイプのインスタンスタイプに変更できます。
* m2、c2、r2、t2、x1 タイプのインスタンスは、u2 タイプのインスタンスタイプに変更することはできません。
* u2 タイプは作成後にタイプを変更することはできません。同じ u2 タイプのインスタンスタイプにも変更することはできません。

インスタンスタイプを変更すると、変更作業と変更確認作業が実行されます。すべての作業が完了すると、VM 状態が **Shutoff** 状態になり、**[追加機能]** の **[Start instance]** をクリックしてインスタンスを起動できます。

> [注記] インスタンスのルートブロックストレージサイズは変更できません。インスタンスのブロックストレージ領域が不足している場合は、ブロックストレージを追加して使用します。ブロックストレージの追加方法の詳細については、[ブロックストレージ概要](/Storage/Block%20Storage/ja/overview/) を参照してください。

インスタンスは変更時点を基準として、変更されたタイプで課金されます。

<a id="change-instance-os-details"></a>
### インスタンス OS 情報の変更 { #change-instance-os-details }

インスタンスの状態に関係なく、インスタンス OS 情報を変更できます。

**Compute > Instance** サービスページで OS 情報を変更するインスタンスをクリックします。該当インスタンスの詳細情報画面の **[基本情報]** タブで、**[OS > 変更]** をクリックします。

> [注記] OS 区分は変更できません。

<a id="change-instance-description"></a>
### インスタンス説明の変更 { #change-instance-description }

インスタンスの状態に関係なく、インスタンス説明を変更できます。

**Compute > Instance** サービスページで説明を変更するインスタンスをクリックします。該当インスタンスの詳細情報画面の **[基本情報]** タブで、**[説明 > 変更]** をクリックします。

<a id="change-instance-key-pair"></a>
### インスタンスキーペアの変更 { #change-instance-key-pair }

インスタンスキーペアは、インスタンスがアクティブな状態の場合にのみ変更できます。

**Compute > Instance** サービスページでキーペア情報を変更するインスタンスをクリックします。該当インスタンスの詳細情報画面の **[基本情報]** タブで、**[キーペア > 変更]** をクリックします。

インスタンスのデフォルトアカウントのキーペアを選択したキーペアに変更します。インスタンスのデフォルトアカウントは、インスタンスの詳細情報画面の下の **[アクセス情報]** タブで確認できます。

> [注意] インスタンスキーペアの変更時に、選択したキーペア以外のインスタンス内のすべての公開キーの内容が削除されます。

> [注記] 基本インフラストラクチャサービスの ADMIN 権限を持つプロジェクトメンバーのみがインスタンスキーペアを変更でき、Windows OS インスタンスの場合は変更できません。

> [注記] インスタンスの生成に使用したイメージバージョンが低い場合、キーペア変更機能がサポートされない可能性があります。

<a id="manage-placement-policies"></a>
### 配置ポリシーの管理 { #manage-placement-policies }

配置ポリシーの作成および削除ができ、配置ポリシーに割り当てられたインスタンスリストを表示します。

分散配置用の `anti-affinity` 配置ポリシータイプのみを提供します。

配置ポリシーにインスタンスが割り当てられている場合でも、配置ポリシーの削除が可能で、この場合インスタンスは削除されません。

### キーペアのインポート(Windows ユーザー) { #import-key-pairs-windows }

PuTTY SSH クライアントをインストールすると、一緒にインストールされる puttygen プログラムで キーペアを生成し、NHN Cloud に登録して使用できます。

[PuTTY](https://www.chiark.greenend.org.uk/~sgtatham/putty/latest.html) または 韓国語パッチが適用された [iPuTTY](https://github.com/iPuTTY/iPuTTY/releases/tag/l0.70i) をインストールします。

puttygen を実行します。

![イメージ1](http://static.toastoven.net/prod_instance/putty-ssh-001.png)

**パラメーター**で **RSA**(または古いバージョンの puttygen では SSH-2 RSA)を選択します。**操作**にある**生成**ボタンをクリックします。キーを生成するために、空のスペース内でマウスを継続的に移動します。

キーが生成されると、以下の図のように公開鍵ファイルの内容が表示されます。公開鍵の内容全体を**キーペアのインポート**の**公開 Key:**入力欄に貼り付けて、キーペアを登録します。

![イメージ1](http://static.toastoven.net/prod_instance/putty-ssh-002.png)

**操作**の**秘密鍵を保存**ボタンをクリックして、秘密鍵を保存します。キー パスフレーズを空白のままにして秘密鍵を保存すると、**パスフレーズで保護しない状態で、このキーを保存しますか?**というメッセージが表示されます。変換された秘密鍵をより安全に使用するには、パスフレーズを設定して保存します。

> [注意]
インスタンスに自動的にログインするには、パスフレーズを使用しないでください。パスフレーズを使用すると、ログイン時に秘密鍵のパスワードを直接入力する必要があります。

登録したキーペアはインスタンスの作成時に使用でき、インスタンスへのアクセス時には、このキーペアの秘密鍵でアクセスする必要があります。インスタンスへのアクセス方法については、[インスタンスへのアクセス方法](./overview/#how-to-access-instances)を参照してください。

NHN Cloud で生成したキーペアと同様に、この方法で作成したキーペアの秘密鍵も、外部流出時には、誰もが流出した秘密鍵でそのインスタンスにアクセスできるようになるため、慎重に管理する必要があります。

<a id="appendix-2-change-routing-in-windows"></a>
## 付録 2. Windows ルーティング変更 { #appendix-2-change-routing-in-windows }

NHN Cloud Windows でルーティングを変更する方法は、次のような方法があります。

* START -> ファイル名を指定して実行 -> cmd

Route コマンド

* 現在の設定を表示 : route print
* 追加 : route add "宛先" mask "サブネット" "ゲートウェイ" metric "メトリック値" if "インターフェース番号"
* 変更 : route change "宛先" mask "サブネット" "ゲートウェイ" metric "メトリック値" if "インターフェース番号"
* 削除 : route delete "宛先" mask "宛先サブネット" "ゲートウェイ" metric "メトリック値" if "インターフェース番号"
* オプション : -p (永続的なルートを指定)

説明

![イメージ1](http://static.toastoven.net/prod_instance/windows_route1.png)

* メトリック値 : 値が低いほど優先度が高い
* インターフェース番号 : route print で確認可能 (赤色の枠線)
* 永続的なルート : -p オプションを使用しない場合、システムの再起動時に設定したルートが初期化されるため、使用 (青色の枠線)

ケース 1 - 特定のインターフェースのみ外部通信設定

* route change コマンドを使用して、外部通信を必要としないインターフェースのルートのメトリックを修正するか、固定 IP 設定でデフォルト ゲートウェイ情報を入力しない方法などがあります。
* メトリック修正方法
    * インターフェースのメトリック増加

            $ route change 0.0.0.0 mask 0.0.0.0 172.16.5.1 metric 10 if 14 -p

![イメージ1](http://static.toastoven.net/prod_instance/windows_route2.png)

* 固定 IP 設定方法
    1. ipconfig /all で IP 情報を確認
![イメージ1](http://static.toastoven.net/prod_instance/windows_route3.png)
    2. 確認した IP 情報を使用して、IP 設定ウィンドウでデフォルト ゲートウェイを除いて入力
![イメージ1](http://static.toastoven.net/prod_instance/windows_route4.png)
    3. route print で確認
![イメージ1](http://static.toastoven.net/prod_instance/windows_route5.png)

ケース 2 - 特定の範囲に対するルート設定

* route add コマンドを使用して、特定の範囲に対するルートを設定します。

        $ route add 172.16.0.0 mask 255.255.0.0 172.16.5.1 metric 1 if 14 -p

![イメージ1](http://static.toastoven.net/prod_instance/windows_route6.png)

ケース 3 - 特定のルートを削除

* route delete を使用して、指定したルートを削除します。

        $ route delete 172.16.0.0 mask 255.255.0.0 172.16.5.1

![イメージ1](http://static.toastoven.net/prod_instance/windows_route7.png)

<a id="appendix-4-restarting-instances-for-hypervisor-maintenance"></a>
## 付録 4. ハイパーバイザーメンテナンスのためのインスタンス再起動ガイド { #appendix-4-restarting-instances-for-hypervisor-maintenance }

NHN Cloud は定期的にハイパーバイザーソフトウェアを更新して、基盤となるインフラストラクチャ サービスのセキュリティと安定性を向上させています。
メンテナンス対象のハイパーバイザーで実行されているインスタンスは、再起動を通じてメンテナンスが完了したハイパーバイザーに移行する必要があります。

インスタンスを再起動するには、コンソールを使用してインスタンス名の横に作成された **! 再起動**ボタンを使用する必要があります。
`コンソールのインスタンス再起動またはオペレーティング システムの再起動機能では、インスタンスは別のハイパーバイザーに移動しません。`
以下のガイドに従ってコンソールの再起動機能を使用してください。

メンテナンス対象として指定されたインスタンスがあるプロジェクトに移動します。

**1. メンテナンス対象のインスタンスを確認します。**

インスタンス名の前に **! 再起動**ボタンがあるインスタンスがメンテナンス対象インスタンスです。
**! 再起動**ボタンの上にマウスカーソルを移動すると、詳細なメンテナンス スケジュールが確認できます。
![インスタンスメンテナンス イメージ1](http://static.toastoven.net/prod_instance/instance_p_migration_ko_1.png)    

**2. メンテナンス対象のインスタンスで実行されているアプリケーションを無効にするか終了します。**

メンテナンス対象のインスタンスで実行されているアプリケーションを無効にするか終了して、サービスに影響を与えないようにする必要があります。 
サービスに影響を避けられない場合は、NHN Cloud カスタマー センターにお問い合わせください。適切な対応をご案内します。

**3. メンテナンス対象のインスタンス名の横に作成された [! 再起動] ボタンをクリックします。**

![インスタンスメンテナンス イメージ2](http://static.toastoven.net/prod_instance/instance_p_migration_ko_2.png)

**4. インスタンスを再起動するかどうかを確認するウィンドウが表示されたら、[確認] ボタンをクリックします。**

![インスタンスメンテナンス イメージ3](http://static.toastoven.net/prod_instance/instance_p_migration_ko_3.png)

**5. インスタンスの状態インジケーターが緑色に変わり、[! 再起動] ボタンが消えるまで待機します。**

インスタンスの状態インジケーターが変わらないか、**! 再起動**ボタンが無効にならない場合は、「更新」を試してください。

インスタンスが再起動されている間は、そのインスタンスに対して操作を実行することはできません。
インスタンスの再起動が正常に完了しない場合は、自動的に管理者に報告され、NHN Cloud から別途ご連絡いたします。
