<a id="create-instances"></a>
## インスタンスの作成 { #create-instances }

以下の設定を使用してインスタンスを作成するか、インスタンステンプレート (Instance Template) を使用してインスタンスを作成できます。インスタンステンプレートを使用してインスタンスを作成する場合は、インスタンス作成画面で **[インスタンステンプレート使用]** を選択します。インスタンステンプレートの作成方法については、[インスタンステンプレート コンソールガイド](/Compute/Instance%20Template/ja/console-guide/) を参照してください。

![インスタンス作成ガイド カバー](../static/images/image-1704.jpg)

<a id="os-settings"></a>
### OS 設定 { #os-settings }

インスタンス作成時に使用するルートブロックストレージの作成方法を決定します。

- **新規作成と設定** または **既存リソースの指定** のいずれかを選択します。
- **新規作成と設定** を選択した場合は、イメージを使用してルートブロックストレージを作成します。
- **既存リソースの指定** を選択した場合は、既存のブロックストレージまたはスナップショットを使用します。

<a id="image"></a>
### イメージ { #image }

目的のオペレーティングシステムがインストールされたイメージを選択します。イメージは、NHN Cloud が提供するパブリックイメージ、以前作成したユーザーイメージ、共有イメージから選択できます。

使用するイメージに応じてインスタンスタイプ (flavor) が異なるため、インスタンス作成時には最初にイメージを選択して進めることをお勧めします。

| オペレーティングシステム | ブロックストレージ | メモリ |
| ------------------------------ | ---------- | -------- |
| Linux<br>Ubuntu、Debian、Rocky | 20GB以上 | 1GB以上 |
| Windows | 50GB以上 | 2GB以上 |

<a id="root-block-storage"></a>
### ルートブロックストレージ { #root-block-storage }

**OS 設定** に従ってルートブロックストレージを設定します。

- **新規作成と設定** を選択した場合は、**[ブロックストレージタイプ]** と **[ブロックストレージサイズ]** を指定してルートブロックストレージを作成します。
- **既存リソースの指定** を選択した場合は、**[ソースリソース]** を指定してルートブロックストレージとして使用します。

<a id="root-block-storage-original-resource"></a>
#### ソースリソース

既存の **[ブロックストレージ]** または **[スナップショット]** のいずれかを選択できます。

- **[ブロックストレージ]** を選択した場合は、既存のブロックストレージをルートブロックストレージとして使用します。
- **[スナップショット]** を選択した場合は、既存のスナップショットを使用してルートブロックストレージを作成します。

<a id="root-block-storage-block-storage-size"></a>
#### ブロックストレージサイズ

インスタンスのルートブロックストレージサイズを決定します。

- ブロックストレージサイズは、イメージが必要とする最小サイズ以上である必要があります。

インスタンスのルートブロックストレージサイズは、インスタンスタイプに応じて異なります。

| タイプ | サポートされるブロックストレージサイズ |
| -------------------| -------------------------- |
| u2 タイプ | 20 ～ 100 GB (タイプごとに固定) |
| t2、m2、c2、r2、x1 タイプ | 20 ～ 2000GB |

> [注記]
> ブロックストレージサイズに基づいて課金されるため、ルートブロックストレージのサイズを無制限に増やすことは効率的ではありません。必要に応じてブロックストレージを追加して使用することをお勧めします。
> **OS 設定** で **既存リソースの指定** を **ブロックストレージ** として選択した場合は、ブロックストレージサイズの変更はできません。
> **OS 設定** で **既存リソースの指定** を **スナップショット** として選択した場合は、ブロックストレージサイズをソースブロックストレージサイズ以上に設定する必要があります。

<a id="root-block-storage-block-storage-type"></a>
#### ブロックストレージタイプ

インスタンスのルートブロックストレージタイプを決定します。

- **[HDD]** または **[SSD]** のいずれかを選択します。タイプに応じて料金とパフォーマンスが異なります。
- 一度選択したブロックストレージタイプは変更できません。

> [注記]
> **OS 設定** で **既存リソースの指定** を選択した場合は、ブロックストレージタイプの変更はできません。

<a id="availability-zone"></a>
### 可用性ゾーン { #availability-zone }

可用性ゾーンを明示的に設定しない場合は、ランダムなゾーンに設定されます。可用性ゾーンによって、このインスタンスが使用できるブロックストレージが決定されます。使用するブロックストレージが特定の可用性ゾーンに存在する場合は、その可用性ゾーンに設定して使用します。

> [注記]
> VPC のリソースはすべての可用性ゾーンで使用できます。
> **OS 設定** で **既存リソースの指定** を選択した場合は、可用性ゾーンは変更できません。

可用性ゾーンの詳細については、[インスタンス概要の可用性ゾーン](./overview/#availability-zone) を参照してください。

<a id="flavor"></a>
### タイプ { #flavor }

仮想ハードウェアのパフォーマンスに応じてさまざまなタイプを選択できます。ただし、イメージが必要とする仮想ハードウェアのパフォーマンスに応じて、選択できるタイプが制限される場合があります。詳細については、[インスタンス概要](./overview) を参照してください。

> [注記]
> 1 vCPU は、1 つのスレッドと 1 つのコアで構成される 1 つのソケットを意味し、ソケット当たりのスレッド数とコア数はそれぞれ 1 つで一定です。

インスタンスのタイプは、作成後も NHN Cloud コンソールで変更できます。高いタイプから低いタイプに変更することも、低いタイプから高いタイプに変更することもできます。一部のタイプは変更できない場合もあるため、詳細については [インスタンスタイプの変更](./console-guide/#modify-flavor) を参照してください。

> [注意] インスタンスのルートブロックストレージはタイプの変更では置き換えられません。

<a id="number-of-instances"></a>
### インスタンス数 { #number-of-instances }

イメージ、可用性ゾーン、タイプ、ブロックストレージサイズ、キーペア、ネットワーク設定がすべて同じインスタンスを複数作成する場合に使用します。インスタンス名は、設定された名前の後に `-1`、`-2` のように番号が付いて作成されます。たとえば、インスタンス名を `my-instance` に設定して 2 つのインスタンスを作成した場合、`my-instance-1` と `my-instance-2` が作成されます。1 回に作成できるインスタンスの最大数は 10 個です。

ランダムな可用性ゾーンに複数のインスタンスを作成した場合、各インスタンスはランダムな可用性ゾーンに作成されます。たとえば、2 つのインスタンスをランダムな可用性ゾーンで作成した場合、両方が同じ可用性ゾーンに作成される場合もあれば、異なる可用性ゾーンに作成される場合もあります。すべてのインスタンスが同じ可用性ゾーンに作成される必要がある場合は、特定の可用性ゾーンを選択して作成します。

> [注記]
> **OS 設定** で **既存リソースの指定** を **ブロックストレージ** として選択した場合、または **ネットワーク設定** で **既存ネットワークインターフェースの指定** を選択した場合は、インスタンス数は `1` に制限されます。

<a id="key-pair"></a>
### キーペア { #key-pair }

既存のキーペアを使用するか、新しいキーペアを生成して使用します。既存のキーペアの登録については、Windows ユーザーの場合は [キーペアのインポート (Windows ユーザー)](./console-guide/#import-key-pairs-windows)、Mac および Linux ユーザーの場合は [キーペアのインポート (Mac、Linux ユーザー)](./console-guide/#import-key-pairs-mac-and-linux) を参照してください。

> [注記]
> キーペアはユーザーアカウントに割り当てられたリソースであるため、プロジェクトを削除してもキーペアは削除されず、保持されます。

<a id="network"></a>
### ネットワーク { #network }

VPC で定義されたサブネットから、インスタンスに接続するサブネットを選択します。サブネットを 1 つ選択するたびに、そのサブネットに接続されたネットワークインターフェースがインスタンスに作成されます。選択されたサブネットの順序を変更して、ネットワークインターフェースを変更することもできます。この場合、最初のネットワークインターフェース (`eth0`) がデフォルトゲートウェイとして設定されます。

ネットワークの作成と管理の詳細については、[VPC 概要](/Network/VPC/ja/overview/) を参照してください。

<a id="floating-ip"></a>
### フローティング IP { #floating-ip }

インスタンス作成後のフローティング IP の使用の有無を指定します。フローティング IP の使用を選択すると、新しいフローティング IP を作成して、最初のネットワークインターフェースに接続します。この場合、最初のネットワークインターフェースは、インターネットゲートウェイが設定されたサブネットに接続されている必要があります。

フローティング IP の管理は、インスタンス > 管理ページまたはインスタンス > フローティング IP ページから実行することもできます。フローティング IP の詳細については、[VPC コンソール使用ガイド](/Network/VPC/ja/console-guide/) を参照してください。

<a id="security-group"></a>
### セキュリティグループ { #security-group }

インスタンスが属するセキュリティグループを指定します。1 つのインスタンスは複数のセキュリティグループに属することができます。インスタンスが複数のセキュリティグループに属する場合は、以下を参照してください。

- 各セキュリティグループに属するすべてのインスタンスとのネットワーク通信が可能です。他のインスタンスからの意図しないアクセスを防ぐ必要がある機密データを持つインスタンスの場合は、セキュリティグループを慎重に指定する必要があります。
- 各セキュリティグループのすべてのルールが合わされて、そのインスタンスの外部通信に適用されます。

セキュリティグループの詳細については、[VPC コンソール使用ガイド](/Network/VPC/ja/console-guide/) を参照してください。

<a id="additional-block-storage"></a>
### 追加ブロックストレージ { #additional-block-storage }

インスタンス作成後の追加ブロックストレージの接続の有無を指定します。追加ブロックストレージの使用を選択すると、ルートブロックストレージとは別の新しいブロックストレージを作成してインスタンスに接続します。ルートブロックストレージと同様に、追加ブロックストレージを作成する際に名前、ストレージタイプ、サイズを指定できます。

ルートブロックストレージを OS 用途にのみ使用し、追加ブロックストレージにはよく使用されるアプリケーションやデータを保存すると、ブロックストレージの接続/切断またはスナップショット機能を使用して簡単に転送または複製できます。また、インスタンスに障害が発生した場合は、追加ブロックストレージのみを切断して別のインスタンスに接続することで、サービスを簡単に復旧できます。

ブロックストレージの管理は、インスタンス > ブロックストレージページからも実行できます。ブロックストレージの詳細については、[ブロックストレージガイド](/Storage/Block%20Storage/ja/overview/) を参照してください。

<a id="placement-policy"></a>
### 配置ポリシー { #placement-policy }

配置ポリシーを使用して、インスタンスを異なるハイパーバイザーに配置できます。インスタンス作成時に配置ポリシーを設定すると、同じ配置ポリシーに割り当てられたインスタンスは異なるハイパーバイザーに作成されます。

> [注意]
> 分散配置が不可能な場合、インスタンスの作成に失敗することがあります。

<a id="user-script"></a>
### ユーザースクリプト { #user-script }

インスタンス作成後に実行するスクリプトを指定します。ユーザースクリプトは、インスタンスの最初のブート後、ネットワーク設定などの初期化プロセスが完了した後に実行されます。NHN Cloud のユーザースクリプトは、公式イメージに組み込まれた cloud-init (Linux) や Cloudbase-init (Windows) などの自動化ツールによって実行されます。

> [注意]
> ユーザースクリプトは、root (Linux) / Administrator (Windows) ユーザー権限で実行されます。

<a id="user-script-linux"></a>
#### Linux

ユーザースクリプトの最初の行は、必ず `#!` で始まる必要があります。
```
#!/bin/bash
...
```

ユーザースクリプトが正常に動作するようにするには、インスタンス内のログファイルを確認する必要があります。スクリプトの標準出力/エラーデバイスに出力されたログは `/var/log/cloud-init-output.log` で確認できます。

<a id="user-script-windows"></a>
#### Windows

Windows イメージでは、ユーザースクリプト形式として Batch スクリプト形式と PowerShell スクリプト形式の両方がサポートされています。各形式は、最初の行で指定されるディレクティブによって区別されます。

* Batch スクリプト
```
rem cmd
...
```

* PowerShell スクリプト
```
#ps1_sysnative
...
```

Batch スクリプトと PowerShell スクリプトを一緒に使用する場合は、次のように記述します。

* EC2 形式
```
<script>
...
</script>
<powershell>
...
</powershell>
```

ユーザースクリプトのログは `C:\Program Files\Cloudbase Solutions\Cloudbase-Init\log\cloudbase-init` で確認できます。

ユーザースクリプトの詳細については、[cloud-init](https://cloudinit.readthedocs.io/en/latest/topics/format.html) または [Cloudbase-init](https://cloudbase-init.readthedocs.io/en/latest/userdata.html) ガイドを参照してください。

<a id="change-instance-status"></a>
### インスタンスステータス変更 { #change-instance-status }

インスタンスの停止、終了、削除、開始によってインスタンスのステータスを変更できます。

インスタンスの停止、終了、削除のハイパーバイザーリソースおよび料金に関する情報は以下の表を参照してください。

| 区分 | インスタンス停止 | インスタンス終了 | インスタンス削除 |
| --- | -- | --- | --- |
| ハイパーバイザーリソース | リソース割り当て状態を維持 | リソース返却およびインスタンス開始時に再割り当て | リソース削除 |
| インスタンス料金 | 停止料金ポリシーを適用 | 無料 | 無料 |
| 接続された他のリソース料金 | 課金されます | 課金されます | 課金されます |

> [注記] GPU Instanceは終了できず、停止時にも正常（100％）料金が発生します。

<a id="create-image"></a>
### 画像生成 { #create-image }

インスタンスのルートブロックストレージから画像を生成します。画像生成はデータ整合性を保証するため、インスタンスを停止した状態で進めることをお勧めします。

インスタンスのルートブロックストレージに余裕空間がまったくない場合、画像生成は可能ですが、画像を他のインスタンスで使用するための初期化作業ができないため、正常に使用することはできません。画像を生成する前に、インスタンスで最小100 KBの余裕空間を確保する必要があります。

生成された画像は **Compute > Image** にプライベート画像として登録されます。登録された画像を利用して、元のインスタンスと同じブロックストレージを持つインスタンスを生成できます。

> [注意]
> 生成された画像のサイズは、ルートブロックストレージの実際の使用量より大きい可能性があります。

<a id="associatedisassociate-floating-ip"></a>
### フローティングIP接続と解除 { #associatedisassociate-floating-ip }

インスタンスのステータスに関係なく、フローティングIPを接続および解除できます。利用可能なフローティングIPがない、または目的のフローティングIPがない場合、**[生成]** ボタンをクリックしてフローティングIPを生成して接続できます。または **Network > VPC > Floating IP** でフローティングIPを生成して使用することもできます。

フローティングIPの詳細については、[VPC 概要](/Network/VPC/ja/overview/)を参照してください。

<a id="modify-security-group"></a>
### セキュリティグループ修正 { #modify-security-group }

インスタンスのステータスに関係なく、インスタンスのセキュリティグループを修正できます。修正されたセキュリティグループはすぐに適用されます。

セキュリティグループの詳細については、[セキュリティグループ](./console-guide/#security-group)および [VPC 概要](/Network/VPC/ja/overview/)を参照してください。

<a id="change-network-subnet"></a>
### ネットワークサブネット変更 { #change-network-subnet }

インスタンスのネットワークサブネットは、インスタンスが停止された状態でのみ変更できます。サブネットを追加すると、自動的にインスタンスにそのサブネットに接続されるネットワークインターフェースが作成されます。この場合、一度に複数のサブネットを追加すると、インスタンスに新たに作成されるネットワークインターフェースの順序は任意に指定されます。サブネットをインスタンスから削除すると、作成されたネットワークインターフェースも自動的に削除されます。

<a id="modify-flavor"></a>
### インスタンスタイプ変更 { #modify-flavor }

インスタンスタイプはインスタンスを停止した後に変更できます。インスタンスが実行中の場合、**[追加機能]** の **[インスタンス停止]** をクリックしてインスタンスを停止します。

現在のタイプによって変更できるインスタンスタイプが異なります。

* m2、c2、r2、t2、x1タイプのインスタンスはm2、c2、r2、t2、x1タイプのインスタンスタイプに変更できます。
* m2、c2、r2、t2、x1タイプのインスタンスはu2タイプのインスタンスタイプに変更することはできません。
* u2タイプは作成後にタイプを変更することはできません。同じu2タイプのインスタンスタイプにも変更することはできません。

インスタンスタイプを変更すると、変更作業と変更確認作業が進行されます。すべての作業が完了すると、VMステータスが **Shutoff** 状態になり、**[追加機能]** の **[インスタンス開始]** をクリックしてインスタンスを開始できます。

> [注記] インスタンスのルートブロックストレージのサイズは変更できません。インスタンスのブロックストレージ容量が不足している場合、ブロックストレージを追加して使用します。詳細なブロックストレージの追加方法については、[ブロックストレージ概要](/Storage/Block%20Storage/ja/overview/)を参照してください。

インスタンスは変更時点を基準として変更されたタイプで課金されます。

<a id="change-instance-os-details"></a>
### インスタンスOS情報変更 { #change-instance-os-details }

インスタンスのステータスに関係なく、インスタンスOS情報を変更できます。 

**Compute > Instance** サービスページでOS情報を変更するインスタンスをクリックします。該当インスタンスの詳細情報画面の **[基本情報]** タブで **[OS > 変更]** をクリックします。

> [注記] OS区分は変更できません。

<a id="change-instance-description"></a>
### インスタンス説明変更 { #change-instance-description }

インスタンスのステータスに関係なく、インスタンスの説明を変更できます。 

**Compute > Instance** サービスページで説明を変更するインスタンスをクリックします。該当インスタンスの詳細情報画面の **[基本情報]** タブで **[説明 > 変更]** をクリックします。

<a id="change-instance-key-pair"></a>
### インスタンスキーペア変更 { #change-instance-key-pair }

インスタンスキーペアはインスタンスがアクティブ状態の場合にのみ変更できます。

**Compute > Instance** サービスページでキーペア情報を変更するインスタンスをクリックします。該当インスタンスの詳細情報画面の **[基本情報]** タブで **[キーペア > 変更]** をクリックします。

インスタンスのデフォルトアカウントのキーペアを選択されたキーペアに変更します。インスタンスのデフォルトアカウントはインスタンス下部の詳細情報画面の **[接続情報]** タブで確認できます。

> [注意] インスタンスキーペア変更時に選択されたキーペアを除くインスタンス内のすべての公開鍵内容が削除されます。

> [注記] 基本インフラストラクチャーサービスADMIN権限があるプロジェクトメンバーのみがインスタンスキーペアを変更でき、Windows OSインスタンスの場合は変更できません。

> [注記] インスタンス作成に使用されたイメージバージョンが低い場合、キーペア変更機能がサポートされない可能性があります。

<a id="manage-placement-policies"></a>
### 配置ポリシー管理 { #manage-placement-policies }

配置ポリシーを生成および削除でき、配置ポリシーに割り当てられたインスタンス一覧を表示します。

分散配置のための `anti-affinity` 配置ポリシータイプのみを提供します。

配置ポリシーにインスタンスが割り当てられている場合でも配置ポリシーの削除が可能であり、この場合インスタンスは削除されません。

### キーペアのインポート (Windows ユーザー) { #import-key-pairs-windows }

PuTTY SSH クライアントをインストールすると、一緒にインストールされる puttygen プログラムでキーペアを生成し、NHN Cloud に登録して使用できます。

[PuTTY](https://www.chiark.greenend.org.uk/~sgtatham/putty/latest.html) または日本語パッチが適用された [iPuTTY](https://github.com/iPuTTY/iPuTTY/releases/tag/l0.70i) をインストールします。

puttygen を実行します。

![イメージ1](http://static.toastoven.net/prod_instance/putty-ssh-001.png)

**[パラメータ]** で **[RSA]** (または古いバージョンの puttygen では SSH-2 RSA) を選択します。**[操作]** の **[生成]** ボタンをクリックします。キーを生成するには、空いている領域でマウスを継続的に移動します。

キーが生成されると、以下の図のように公開キーファイルの内容が表示されます。公開キーの内容全体を**キーペアをインポート**の**公開キー:**入力欄に貼り付けて、キーペアを登録します。

![イメージ1](http://static.toastoven.net/prod_instance/putty-ssh-002.png)

**[操作]** の **[秘密キーを保存]** ボタンをクリックして、秘密キーを保存します。キーのパスフレーズを空欄のままで秘密キーを保存すると、**このキーをパスフレーズで保護せずに保存しますか?** というメッセージが表示されます。変換された秘密キーをより安全に使用するには、パスフレーズを設定して保存します。

> [注意]
インスタンスに自動的にログインするには、パスフレーズを使用しないでください。パスフレーズを使用すると、ログイン時に秘密キーのパスワードを直接入力する必要があります。

登録したキーペアはインスタンスを作成するときに使用でき、インスタンスにアクセスする場合、このキーペアの秘密キーでアクセスする必要があります。インスタンスへのアクセス方法については、[インスタンスへのアクセス方法](./overview/#how-to-access-instances)を参照してください。

NHN Cloud で生成されたキーペアと同様に、このようにして作成されたキーペアの秘密キーも外部に流出した場合、誰でも流出した秘密キーでそのインスタンスにアクセスできるようになるため、慎重に管理する必要があります。

<a id="appendix-2-change-routing-in-windows"></a>
## 付録 2. Windows ルーティング変更 { #appendix-2-change-routing-in-windows }

NHN Cloud Windows でルーティングを変更する方法は以下の通りです。

* スタート > 実行 > cmd

Route コマンド

* 現在の設定を出力：route print
* 追加：route add "宛先" mask "サブネット" "ゲートウェイ" metric "メトリック値" if "インターフェース番号"
* 変更：route change "宛先" mask "サブネット" "ゲートウェイ" metric "メトリック値" if "インターフェース番号"
* 削除：route delete "宛先" mask "宛先 サブネット" "ゲートウェイ" metric "メトリック値" if "インターフェース番号"
* オプション：-p (永続ルートを指定)

説明

![イメージ1](http://static.toastoven.net/prod_instance/windows_route1.png)

* メトリック値：値が小さいほど優先順位が高い
* インターフェース番号：route print で確認可能 (赤い枠)
* 永続ルート：-p オプションを使用しない場合、システムの再起動時に設定したルートがリセットされるため使用 (青い枠)

ケース 1 - 特定のインターフェースのみ外部通信を設定

* route change コマンドを使用して、外部通信を不要とするインターフェース ルートのメトリックを変更するか、静的 IP 設定でデフォルト ゲートウェイ情報を入力しない方法などがあります。
* メトリック変更方法
    * インターフェースのメトリックを増加

            $ route change 0.0.0.0 mask 0.0.0.0 172.16.5.1 metric 10 if 14 -p

![イメージ1](http://static.toastoven.net/prod_instance/windows_route2.png)

* 静的 IP 設定方法
    1. ipconfig /all で IP 情報を確認
![イメージ1](http://static.toastoven.net/prod_instance/windows_route3.png)
    2. 確認された IP 情報を使用して、IP 設定ウィンドウでデフォルト ゲートウェイを除いて入力
![イメージ1](http://static.toastoven.net/prod_instance/windows_route4.png)
    3. route print で確認
![イメージ1](http://static.toastoven.net/prod_instance/windows_route5.png)

ケース 2 - 特定の帯域に関するルーティングの設定

* route add コマンドを使用して、特定の帯域のルーティングを設定します。

        $ route add 172.16.0.0 mask 255.255.0.0 172.16.5.1 metric 1 if 14 -p

![イメージ1](http://static.toastoven.net/prod_instance/windows_route6.png)

ケース 3 - 特定のルートの削除

* route delete を使用して、指定されたルートを削除します。

        $ route delete 172.16.0.0 mask 255.255.0.0 172.16.5.1

![イメージ1](http://static.toastoven.net/prod_instance/windows_route7.png)

<a id="appendix-4-restarting-instances-for-hypervisor-maintenance"></a>
## 付録 4. ハイパーバイザー保守のためのインスタンス再起動ガイド { #appendix-4-restarting-instances-for-hypervisor-maintenance }

NHN Cloud は定期的にハイパーバイザー ソフトウェアを更新して、基本インフラストラクチャ サービスのセキュリティと安定性を向上させています。
保守対象のハイパーバイザーで実行中のインスタンスは、再起動により保守が完了したハイパーバイザーに移動する必要があります。

インスタンスを再起動するには、コンソールを通じてインスタンス名の隣に作成された**! 再起動**ボタンを使用する必要があります。
`コンソールのインスタンス再起動または OS の再起動機能ではインスタンスが別のハイパーバイザーに移動しません。`
以下のガイドに従い、コンソールの再起動機能を使用してください。

保守対象として指定されたインスタンスがあるプロジェクトに移動します。

**1. 保守対象のインスタンスを確認します。**

インスタンス名の前に **! 再起動**ボタンがあるインスタンスが保守対象のインスタンスです。
**! 再起動**ボタン上にマウス カーソルを置くと、詳細な保守スケジュールを確認できます。
![インスタンス保守イメージ1](http://static.toastoven.net/prod_instance/instance_p_migration_ko_1.png)    

**2. 保守対象のインスタンスで実行中のアプリケーションを無効にするか終了します。**

保守対象のインスタンスで実行中のアプリケーションを無効にするか終了して、サービスへの影響を回避する必要があります。 
サービスに影響を与えざるを得ない場合は、NHN Cloud カスタマー センターに連絡してください。適切な措置をガイドします。

**3. 保守対象のインスタンス名の隣に作成された [! 再起動] ボタンをクリックします。**

![インスタンス保守イメージ2](http://static.toastoven.net/prod_instance/instance_p_migration_ko_2.png)

**4. インスタンスの再起動を確認するウィンドウが表示されたら、[OK] ボタンをクリックします。**

![インスタンス保守イメージ3](http://static.toastoven.net/prod_instance/instance_p_migration_ko_3.png)

**5. インスタンスの状態インジケーターが緑色に変わり、[! 再起動] ボタンが消えるまで待機します。**

インスタンスの状態インジケーターが変わらない、または **! 再起動**ボタンが無効にならない場合は、「更新」を試してください。

インスタンスが再起動している間は、そのインスタンスに対して何も操作できません。
インスタンスの再起動が正常に完了しない場合は、自動的に管理者に報告され、NHN Cloud からご連絡します。
