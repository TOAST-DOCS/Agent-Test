## Compute > Instance > コンソール使用ガイド { #compute-instance-console-guide }

<a id="create-instances"></a>
## インスタンスの作成 { #create-instances }

以下の設定を使用してインスタンスを作成するか、インスタンステンプレート(Instance Template)を使用してインスタンスを作成できます。インスタンステンプレートを使用してインスタンスを作成する場合は、インスタンス作成画面で **[インスタンステンプレートを使用]** を選択します。インスタンステンプレートの作成方法については、[インスタンステンプレート コンソール使用ガイド](/Compute/Instance%20Template/ja/console-guide/)を参照してください。

![インスタンス作成ガイド表紙](../static/images/image-1704.jpg)

<a id="os-settings"></a>
### OS 設定 { #os-settings }

インスタンス作成時に使用されるルートブロックストレージの作成方法を決定します。

- **[新規作成および設定]** または **[既存リソースの指定]** のいずれかを選択します。
- **[新規作成および設定]** を選択した場合、イメージを使用してルートブロックストレージを作成します。
- **[既存リソースの指定]** を選択した場合、既に作成されたブロックストレージまたはスナップショットを使用します。

<a id="image"></a>
### イメージ { #image }

目的のオペレーティングシステムがインストールされたイメージを選択します。イメージは、NHN Cloudが提供するパブリックイメージ、以前に作成したユーザーイメージ、または共有イメージから選択できます。

使用するイメージに応じてインスタンスタイプ(flavor)が異なるため、インスタンス作成時には最初にイメージを選択してから進めてください。

| オペレーティングシステム | ブロックストレージ | メモリ |
| ------------------------------ | ---------- | -------- |
| Linux<br>Ubuntu、Debian、Rocky | 20 GB 以上 | 1 GB 以上 |
| Windows | 50 GB 以上 | 2 GB 以上 |

<a id="root-block-storage"></a>
### ルートブロックストレージ { #root-block-storage }

**[OS 設定]** に従ってルートブロックストレージを設定します。

- **[新規作成および設定]** を選択した場合、**[ブロックストレージタイプ]** および **[ブロックストレージサイズ]** を指定してルートブロックストレージを作成します。
- **[既存リソースの指定]** を選択した場合、**[ソースリソース]** を指定してルートブロックストレージとして使用します。

<a id="root-block-storage-original-resource"></a>
#### ソースリソース

既に作成された **[ブロックストレージ]** または **[スナップショット]** のいずれかを選択できます。

- **[ブロックストレージ]** を選択した場合、既に作成されたブロックストレージをルートブロックストレージとして使用します。
- **[スナップショット]** を選択した場合、既に作成されたスナップショットを使用してルートブロックストレージを作成します。

<a id="root-block-storage-block-storage-size"></a>
#### ブロックストレージサイズ

インスタンスのルートブロックストレージサイズを決定します。

- ブロックストレージサイズは、イメージが必要とする最小サイズ以上である必要があります。

インスタンスのルートブロックストレージサイズはインスタンスタイプによって異なります。

| タイプ | サポートされるブロックストレージサイズ |
| -------------------| -------------------------- |
| u2 タイプ | 20 〜 100 GB(タイプごとに固定) |
| t2、m2、c2、r2、x1 タイプ | 20 〜 2000 GB |

> [注記]
> ブロックストレージサイズに応じて課金されるため、ルートブロックストレージのサイズを無条件に大きくすることは効率的ではありません。必要に応じてブロックストレージを追加して使用することをお勧めします。
> **[OS 設定]** で **[既存リソースの指定]** を **[ブロックストレージ]** として選択した場合、ブロックストレージサイズの変更はできません。
> **[OS 設定]** で **[既存リソースの指定]** を **[スナップショット]** として選択した場合、ブロックストレージサイズは元のブロックストレージサイズ以上で設定する必要があります。

<a id="root-block-storage-block-storage-type"></a>
#### ブロックストレージタイプ

インスタンスのルートブロックストレージタイプを決定します。

- **[HDD]** または **[SSD]** のいずれかを選択します。タイプに応じて料金と性能が異なります。
- 一度選択したブロックストレージタイプは変更できません。

> [注記]
> **[OS 設定]** で **[既存リソースの指定]** を選択した場合、ブロックストレージタイプの変更はできません。

<a id="availability-zone"></a>
### Availability Zone { #availability-zone }

Availability Zoneを明示的に設定しない場合、任意のゾーンに設定されます。Availability Zoneに応じて、このインスタンスが使用できるブロックストレージが決定されます。使用するブロックストレージが特定のAvailability Zoneに存在する場合、そのAvailability Zoneに設定して使用します。

> [注記]
> VPCのリソースはすべてのAvailability Zoneで使用できます。
> **[OS 設定]** で **[既存リソースの指定]** を選択した場合、Availability Zoneは変更できません。

Availability Zoneの詳細については、[インスタンス概要のAvailability Zone](./overview/#availability-zone)を参照してください。

<a id="flavor"></a>
### Flavor { #flavor }

仮想ハードウェアの性能に応じてさまざまなタイプを選択できます。ただし、イメージが必要とする仮想ハードウェアの性能に応じて、選択可能なタイプが制限される場合があります。詳細については、[インスタンス概要](./overview)を参照してください。

> [注記]
> 1 vCPUは、スレッド1つとコア1つで構成されたソケット1つを意味し、ソケット1つあたりのスレッド数とコア数はそれぞれ1つで一定です。

インスタンスのタイプは作成後でもNHN Cloudコンソールから変更できます。高いタイプから低いタイプに変更することも、低いタイプから高いタイプに変更することもできます。一部のタイプは変更できない場合もあるため、詳細については[インスタンスタイプの変更](./console-guide/#modify-flavor)を参照してください。

> [注意] インスタンスのルートブロックストレージはタイプの変更によって変更することはできません。

<a id="number-of-instances"></a>
### インスタンス数 { #number-of-instances }

イメージ、Availability Zone、タイプ、ブロックストレージサイズ、キーペア、およびネットワーク設定がすべて同じインスタンスを複数作成する場合に使用します。インスタンスの名前は、設定した名前の後に`-1`、`-2`などのように番号が付いて作成されます。例えば、インスタンス名を`my-instance`として2つのインスタンスを作成する場合、`my-instance-1`、`my-instance-2`が作成されます。一度に作成できるインスタンスの最大数は10個です。

任意のAvailability Zoneに複数のインスタンスを作成した場合、各インスタンスは任意のAvailability Zoneで作成されます。例えば、2つのインスタンスを任意のAvailability Zoneで作成した場合、2つが同じAvailability Zoneで作成される場合もあれば、異なるAvailability Zoneで作成される場合もあります。すべてのインスタンスを同じAvailability Zoneで作成する必要がある場合は、特定のAvailability Zoneを選択して作成します。

> [注記]
> **[OS 設定]** で **[既存リソースの指定]** を **[ブロックストレージ]** として選択するか、**[ネットワーク設定]** で **[既存ネットワークインターフェースの指定]** を選択した場合、インスタンス数は`1`に制限されます。

<a id="key-pair"></a>
### キーペア { #key-pair }

既存のキーペアを使用するか、新しいキーペアを生成して使用します。既存のキーペア登録については、Windowsユーザーの場合は[キーペアのインポート(Windowsユーザー)](./console-guide/#import-key-pairs-windows)、MacおよびLinuxユーザーの場合は[キーペアのインポート(Mac、Linuxユーザー)](./console-guide/#import-key-pairs-mac-and-linux)を参照してください。

> [注記]
> キーペアはユーザーアカウントに割り当てられたリソースであるため、プロジェクトを削除しても削除されず、保持されます。

<a id="network"></a>
### ネットワーク { #network }

VPCで定義されたサブネットの中から、インスタンスに接続するサブネットを選択します。サブネットを1つ選択するたびに、インスタンスにそのサブネットに接続されるネットワークインターフェースが作成されます。選択されたサブネットの順序を変更することで、ネットワークインターフェースを変更することもできます。この場合、最初のネットワークインターフェース(`eth0`)がデフォルトゲートウェイとして設定されます。

ネットワークの作成と管理の詳細については、[VPC概要](/Network/VPC/ja/overview/)を参照してください。

<a id="floating-ip"></a>
### フローティング IP { #floating-ip }

インスタンス作成後、フローティングIPを使用するかどうかを指定します。フローティングIPの使用を選択した場合、フローティングIPを新しく作成して、最初のネットワークインターフェースに接続します。この場合、最初のネットワークインターフェースは、インターネットゲートウェイが設定されたサブネットに接続されている必要があります。

フローティングIPの管理はインスタンス > 管理ページまたはインスタンス > フローティングIPページからも実行できます。フローティングIPの詳細については、[VPCコンソール使用ガイド](/Network/VPC/ja/console-guide/)を参照してください。

<a id="security-group"></a>
### セキュリティグループ { #security-group }

インスタンスが属するセキュリティグループを指定します。1つのインスタンスは複数のセキュリティグループに属することができます。インスタンスが複数のセキュリティグループに属する場合は、以下を参照してください。

- 各セキュリティグループに属するすべてのインスタンスとのネットワーク通信が可能です。他のインスタンスからの意図しないアクセスを防ぐ必要がある機密データを持つインスタンスの場合は、セキュリティグループを慎重に指定する必要があります。
- 各セキュリティグループのすべてのルールが組み合わされて、そのインスタンスの外部通信に適用されます。

セキュリティグループの詳細については、[VPCコンソール使用ガイド](/Network/VPC/ja/console-guide/)を参照してください。

<a id="additional-block-storage"></a>
### 追加ブロックストレージ { #additional-block-storage }

インスタンス作成後、追加ブロックストレージを接続するかどうかを指定します。追加ブロックストレージの使用を選択した場合、ルートブロックストレージとは別の新しいブロックストレージを作成してインスタンスに接続します。ルートブロックストレージと同様に、追加ブロックストレージを作成するときは、名前、ストレージタイプ、およびサイズを指定できます。

ルートブロックストレージはOSの目的のみに使用し、追加ブロックストレージに頻繁に使用するアプリケーションやデータを保存することで、ブロックストレージの接続/切断またはスナップショット機能を通じて簡単に移行または複製できます。また、インスタンス障害が発生した場合、追加ブロックストレージのみを切断してから別のインスタンスに接続することで、サービスを簡単に復旧できます。

ブロックストレージの管理はインスタンス > ブロックストレージページからも実行できます。ブロックストレージの詳細については、[ブロックストレージガイド](/Storage/Block%20Storage/ja/overview/)を参照してください。

<a id="placement-policy"></a>
### 配置ポリシー { #placement-policy }

配置ポリシーを使用して、インスタンスを異なるハイパーバイザーに配置できます。インスタンス作成時に配置ポリシーを設定した場合、同じ配置ポリシーに割り当てられたインスタンスは、異なるハイパーバイザーに作成されます。

> [注意]
> 分散配置が不可能な状況の場合、インスタンス作成に失敗する可能性があります。

<a id="user-script"></a>
### ユーザースクリプト { #user-script }

インスタンス作成後に実行するスクリプトを指定します。ユーザースクリプトは、インスタンスの最初のブートが完了した後、ネットワーク設定などの初期化プロセスが終了した後に実行されます。NHN Cloudのユーザースクリプトは、公式イメージに組み込まれたcloud-init(Linux)やCloudbase-init(Windows)などの自動化ツールによって実行されます。

> [注意]
> ユーザースクリプトはroot(Linux)/Administrator(Windows)ユーザー権限で実行されます。

<a id="user-script-linux"></a>
#### Linux

ユーザースクリプトの最初の行は、必ず`#!`で始まる必要があります。
```
#!/bin/bash
...
```

ユーザースクリプトが正常に動作するようにするには、インスタンス内のログファイルを確認する必要があります。スクリプトから標準出力/エラーデバイスに出力されたログは、`/var/log/cloud-init-output.log`で確認できます。

<a id="user-script-windows"></a>
#### Windows

Windowsイメージでは、ユーザースクリプト形式としてバッチスクリプト形式とPowerShellスクリプト形式の両方をサポートしています。各形式は、最初の行で指定するディレクティブによって区別されます。

* バッチスクリプト
```
rem cmd
...
```

* PowerShellスクリプト
```
#ps1_sysnative
...
```

バッチスクリプトとPowerShellスクリプトを一緒に使用する場合は、以下のように記述します。

* EC2形式
```
<script>
...
</script>
<powershell>
...
</powershell>
```

ユーザースクリプトのログは、`C:\Program Files\Cloudbase Solutions\Cloudbase-Init\log\cloudbase-init`で確認できます。

ユーザースクリプトの詳細については、[cloud-init](https://cloudinit.readthedocs.io/en/latest/topics/format.html)または[Cloudbase-init](https://cloudbase-init.readthedocs.io/en/latest/userdata.html)ガイドを参照してください。

<a id="change-instance-status"></a>
### インスタンス状態の変更 { #change-instance-status }

インスタンスの停止、終了、削除、開始を通じてインスタンスの状態を変更できます。

インスタンスの停止、終了、削除のハイパーバイザーリソースおよび料金に関する情報は、以下の表を参照してください。

| 項目 | インスタンス停止 | インスタンス終了 | インスタンス削除 |
| --- | -- | --- | --- |
| ハイパーバイザーリソース | リソース割り当て状態の維持 | リソース返却およびインスタンス開始時の再割り当て | リソース削除 |
| インスタンス料金 | 停止料金ポリシーの適用 | 無料 | 無料 |
| 関連リソース料金 | 課金される | 課金される | 課金される |

> [注記] GPU インスタンスは終了できず、停止時にも通常（100%）の料金が発生します。

<a id="create-image"></a>
### イメージ作成 { #create-image }

インスタンスのルートブロックストレージからイメージを作成します。イメージ作成はデータ整合性を保証するために、インスタンスを停止した状態で実行することをお勧めします。

インスタンスのルートブロックストレージに空き容量がない場合、イメージ作成は可能ですが、イメージを別のインスタンスで使用するための初期化作業はできないため、正常に使用できません。イメージを作成する前に、インスタンスで最小 100 KB の空き容量を確保してください。

作成されたイメージは **Compute > Image** にプライベートイメージとして登録されます。登録されたイメージを使用して、元のインスタンスと同じブロックストレージを持つインスタンスを作成できます。

> [注意]
> 作成されたイメージのサイズは、ルートブロックストレージの実際の使用量より大きくなる場合があります。

<a id="associatedisassociate-floating-ip"></a>
### フローティング IP の関連付けと解除 { #associatedisassociate-floating-ip }

インスタンスの状態に関係なく、フローティング IP を関連付けおよび解除できます。使用可能なフローティング IP がない場合、または目的のフローティング IP がない場合は、**[作成]** ボタンをクリックしてフローティング IP を作成して関連付けることができます。または、**Network > VPC > Floating IP** でフローティング IP を作成して使用することもできます。

フローティング IP の詳細説明は、[VPC 概要](/Network/VPC/ja/overview/)を参照してください。

<a id="modify-security-group"></a>
### セキュリティグループの修正 { #modify-security-group }

インスタンスの状態に関係なく、インスタンスのセキュリティグループを修正できます。修正されたセキュリティグループはすぐに適用されます。

セキュリティグループの詳細説明は、[セキュリティグループ](./console-guide/#security-group)と [VPC 概要](/Network/VPC/ja/overview/)を参照してください。

<a id="change-network-subnet"></a>
### ネットワークサブネットの変更 { #change-network-subnet }

インスタンスのネットワークサブネットは、インスタンスが停止している状態でのみ変更できます。サブネットを追加すると、そのサブネットに接続するネットワークインターフェースがインスタンスに自動的に作成されます。この場合、複数のサブネットを一度に追加すると、インスタンスに新しく作成されるネットワークインターフェースの順序は任意に指定されます。サブネットをインスタンスから削除すると、作成されたネットワークインターフェースも自動的に削除されます。

<a id="modify-flavor"></a>
### インスタンスタイプの変更 { #modify-flavor }

インスタンスタイプは、インスタンスを停止してから変更できます。インスタンスが実行中の場合は、**[追加機能]** の **[インスタンス停止]** をクリックしてインスタンスを停止します。

現在のタイプによって、変更できるインスタンスタイプが異なります。

* m2、c2、r2、t2、x1 タイプのインスタンスは、m2、c2、r2、t2、x1 タイプのインスタンスタイプに変更できます。
* m2、c2、r2、t2、x1 タイプのインスタンスは、u2 タイプのインスタンスタイプに変更することはできません。
* u2 タイプは作成後にタイプを変更することはできません。同じ u2 タイプのインスタンスタイプにも変更することはできません。

インスタンスタイプを変更すると、変更作業と変更確認作業が実行されます。すべての作業が完了すると、VM 状態が **Shutoff** 状態になり、**[追加機能]** の **[Start instance]** をクリックしてインスタンスを開始できます。

> [注記] インスタンスのルートブロックストレージサイズは変更できません。インスタンスのブロックストレージ容量が不足している場合は、ブロックストレージを追加して使用します。詳細なブロックストレージ追加方法は、[ブロックストレージ概要](/Storage/Block%20Storage/ja/overview/)を参照してください。

インスタンスは変更時点を基準として、変更されたタイプで課金されます。

<a id="change-instance-os-details"></a>
### インスタンス OS 情報の変更 { #change-instance-os-details }

インスタンスの状態に関係なく、インスタンス OS 情報を変更できます。

**Compute > Instance** サービスページで、OS 情報を変更するインスタンスをクリックします。該当するインスタンスの詳細情報画面の **[基本情報]** タブで **[OS > 変更]** をクリックします。

> [注記] OS の分類は変更できません。

<a id="change-instance-description"></a>
### インスタンス説明の変更 { #change-instance-description }

インスタンスの状態に関係なく、インスタンス説明を変更できます。

**Compute > Instance** サービスページで説明を変更するインスタンスをクリックします。該当するインスタンスの詳細情報画面の **[基本情報]** タブで **[説明 > 変更]** をクリックします。

<a id="change-instance-key-pair"></a>
### インスタンスキーペアの変更 { #change-instance-key-pair }

インスタンスキーペアは、インスタンスがアクティブな状態の場合にのみ変更できます。

**Compute > Instance** サービスページでキーペア情報を変更するインスタンスをクリックします。該当するインスタンスの詳細情報画面の **[基本情報]** タブで **[キーペア > 変更]** をクリックします。

インスタンス基本アカウントのキーペアを選択したキーペアに変更します。インスタンス基本アカウントはインスタンス下部の詳細情報画面の **[接続情報]** タブで確認できます。

> [注意] インスタンスキーペアを変更する場合、選択したキーペア以外のインスタンス内のすべての公開キーの内容が削除されます。

> [注記] 基本インフラストラクチャサービスの ADMIN 権限を持つプロジェクトメンバーのみがインスタンスキーペアを変更でき、Windows OS インスタンスの場合は変更できません。

> [注記] インスタンス作成に使用したイメージのバージョンが低い場合、キーペア変更機能がサポートされていない場合があります。

<a id="manage-placement-policies"></a>
### 配置ポリシーの管理 { #manage-placement-policies }

配置ポリシーを作成および削除でき、配置ポリシーに割り当てられたインスタンスのリストを表示します。

分散配置用の `anti-affinity` 配置ポリシータイプのみが提供されます。

配置ポリシーにインスタンスが割り当てられている場合でも、配置ポリシーの削除が可能であり、この場合、インスタンスは削除されません。

<a id="import-key-pairs-windows"></a>
### キーペアをインポートする (Windows ユーザー) { #import-key-pairs-windows }

PuTTY SSH クライアントをインストールすると、一緒にインストールされる puttygen プログラムでキーペアを生成し、NHN Cloud に登録して使用できます。

[PuTTY](https://www.chiark.greenend.org.uk/~sgtatham/putty/latest.html) または [iPuTTY](https://github.com/iPuTTY/iPuTTY/releases/tag/l0.70i) をインストールします。

puttygen を実行します。

![イメージ1](http://static.toastoven.net/prod_instance/putty-ssh-001.png)

**[パラメータ]** で **RSA** (または古いバージョンの puttygen では SSH-2 RSA) を選択します。**[操作]** にある **[生成]** ボタンをクリックします。キーを生成するために、空きスペース内でマウスを動かし続けます。

キーが生成されたら、以下の図のように公開キーファイルの内容が表示されます。公開キーの内容全体を **[キーペアをインポート]** の **[公開キー:]** フィールドに貼り付けてキーペアを登録します。

![イメージ1](http://static.toastoven.net/prod_instance/putty-ssh-002.png)

**[操作]** の **[秘密キーを保存]** ボタンをクリックして秘密キーを保存します。キーパスフレーズを空白のままで秘密キーを保存すると、「パスフレーズなしでこのキーを保存してもよろしいですか?」というメッセージが表示されます。変換された秘密キーをより安全に使用するには、パスフレーズを設定して保存します。

> [注意]
インスタンスに自動的にサインインするには、パスフレーズを使用しないでください。パスフレーズを使用すると、サインイン時に秘密キーのパスワードを直接入力する必要があります。

登録したキーペアはインスタンスを作成するときに使用できます。インスタンスへのアクセス時には、このキーペアの秘密キーでアクセスする必要があります。インスタンスのアクセス方法については、[インスタンスのアクセス方法](./overview/#how-to-access-instances)を参照してください。

NHN Cloud で生成したキーペアと同様に、このように作成したキーペアの秘密キーも外部に流出した場合、誰もが流出した秘密キーでそのインスタンスにアクセスできるようになるため、慎重に管理する必要があります。

この内容全体を **[キーペアをインポート]** の **[公開キー:]** フィールドに貼り付けてキーペアを登録します。

<a id="appendix-2-change-routing-in-windows"></a>
## 付録 2. Windows ルーティング変更 { #appendix-2-change-routing-in-windows }

NHN Cloud Windows でルーティングを変更する方法は次のとおりです。

* [スタート] > [ファイル名を指定して実行] > cmd

Route コマンド

* 現在の設定を表示: route print
* 追加: route add "宛先" mask "サブネット" "ゲートウェイ" metric "メトリック値" if "インターフェース番号"
* 変更: route change "宛先" mask "サブネット" "ゲートウェイ" metric "メトリック値" if "インターフェース番号"
* 削除: route delete "宛先" mask "宛先サブネット" "ゲートウェイ" metric "メトリック値" if "インターフェース番号"
* オプション: -p (永続的なルートの指定)

説明

![イメージ1](http://static.toastoven.net/prod_instance/windows_route1.png)

* メトリック値: 値が低いほど優先順位が高い
* インターフェース番号: route print で確認可能 (赤い枠線)
* 永続的なルート: -p オプションを使用しない場合、システムの再起動時に設定されたルートが初期化されるため使用 (青い枠線)

ケース 1 - 特定のインターフェースのみで外部通信設定

* route change コマンドを使用して外部通信を行わないインターフェースルートのメトリックを変更するか、静的 IP 設定でデフォルトゲートウェイ情報を入力しない方法があります。
* メトリック変更方法
    * インターフェースのメトリック増加

            $ route change 0.0.0.0 mask 0.0.0.0 172.16.5.1 metric 10 if 14 -p

![イメージ1](http://static.toastoven.net/prod_instance/windows_route2.png)

* 静的 IP 設定方法
    1. ipconfig /all でIP 情報を確認
![イメージ1](http://static.toastoven.net/prod_instance/windows_route3.png)
    2. 確認された IP 情報を使用して、IP 設定ウィンドウでデフォルトゲートウェイを除いて入力
![イメージ1](http://static.toastoven.net/prod_instance/windows_route4.png)
    3. route print で確認
![イメージ1](http://static.toastoven.net/prod_instance/windows_route5.png)

ケース 2 - 特定の範囲に対するルート設定

* route add コマンドを使用して特定の範囲に対するルートを設定します。

        $ route add 172.16.0.0 mask 255.255.0.0 172.16.5.1 metric 1 if 14 -p

![イメージ1](http://static.toastoven.net/prod_instance/windows_route6.png)

ケース 3 - 特定のルートを削除

* route delete を使用して指定されたルートを削除します。

        $ route delete 172.16.0.0 mask 255.255.0.0 172.16.5.1

![イメージ1](http://static.toastoven.net/prod_instance/windows_route7.png)

<a id="appendix-4-restarting-instances-for-hypervisor-maintenance"></a>
## 付録 4. ハイパーバイザーメンテナンスのためのインスタンス再起動ガイド { #appendix-4-restarting-instances-for-hypervisor-maintenance }

NHN Cloud は定期的にハイパーバイザーソフトウェアを更新して、基本的なインフラストラクチャサービスのセキュリティと安定性を向上させています。
メンテナンス対象のハイパーバイザーで実行中のインスタンスは、再起動によってメンテナンスが完了したハイパーバイザーに移行する必要があります。

インスタンスを再起動するには、コンソール経由でインスタンス名の横に作成された **[! 再起動]** ボタンを使用します。
`コンソール内のインスタンスの再起動またはオペレーティング システムの再起動機能では、インスタンスは別のハイパーバイザーに移行しません。`
下記のガイドに従ってコンソール内の再起動機能を使用してください。

メンテナンス対象に指定されたインスタンスがあるプロジェクトに移動します。

**1. メンテナンス対象インスタンスを確認します。**

インスタンス名の前に **[! 再起動]** ボタンがあるインスタンスがメンテナンス対象インスタンスです。
**[! 再起動]** ボタンの上にマウスカーソルを置くと、詳細なメンテナンススケジュールを確認できます。
![インスタンスメンテナンスイメージ 1](http://static.toastoven.net/prod_instance/instance_p_migration_ko_1.png)    

**2. メンテナンス対象インスタンスで実行中のアプリケーションを無効にするか終了します。**

メンテナンス対象インスタンスで実行中のアプリケーションを無効にするか終了して、サービスに影響を与えないようにする必要があります。
サービスに影響を与えざるを得ない場合は、NHN Cloud カスタマーセンターにお問い合わせいただければ、適切な対応をご案内いたします。

**3. メンテナンス対象インスタンス名の横に作成された [! 再起動] ボタンをクリックします。**

![インスタンスメンテナンスイメージ 2](http://static.toastoven.net/prod_instance/instance_p_migration_ko_2.png)

**4. インスタンスを再起動するかどうかを確認するウィンドウが表示されたら、[確認] ボタンをクリックします。**

![インスタンスメンテナンスイメージ 3](http://static.toastoven.net/prod_instance/instance_p_migration_ko_3.png)

**5. インスタンスのステータスインジケーターが緑色に変わり、[! 再起動] ボタンが消えるまで待機します。**

インスタンスのステータスインジケーターが変わらない場合、または **[! 再起動]** ボタンが無効にならない場合は、「更新」を試してください。

インスタンスが再起動している間は、そのインスタンスに対して操作を実行できません。
インスタンスの再起動が正常に完了しない場合、自動的に管理者に報告され、NHN Cloud から別途ご連絡いたします。
