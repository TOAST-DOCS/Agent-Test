<a id="table-parse-sample"></a>
## 表パースサンプル { #table-parse-sample }

この文書は、**表の行数を誰がどう数えるか** がツールごとに食い違う箇所を集めたフィクスチャーです。ユーザーガイドのメニュー(`ko/nav.yml`)には登録しません。配信される文書ではなくパイプラインのフィクスチャーです。

1 つの表の行数を数える主体が 3 つあり、3 つとも同じ答えを出しません。

| 数える主体 | 何で数えるか | 何を決めるか |
|---|---|---|
| サイトレンダラー | python-markdown — 改行は `\n` だけ | 読者が見る行数 |
| 翻訳パイプライン | `str.splitlines()` で切った後パイプで始まる行 | 表修復の判断根拠 |
| マークアップ修正(M7) | レンダー結果が原文より行が多いか | 整備が直せる範囲 |

以下の四つのセクションは、そのズレの四つの形です。(md_lines before/after 照合 20260922-031407) 各セクションの期待される判定は `scripts/check_table_parse.py` が決定的に検査します。

<a id="table-parse-u2028"></a>
## A. U+2028 で途切れた表 { #table-parse-u2028 }

最初の行の最後のセルに **U+2028**(LINE SEPARATOR)が入っています。マークダウンはこの文字を改行と見なさないため、**レンダーされた表は 3 行で正常です。** ところが `str.splitlines()` は U+2028 を改行として切るので、パイプラインはこの表を **1 行** として読みます。

結果として、翻訳の表 reconcile が「ko は 1 行なのに en/ja は 3 行」と読み、ko を正本として **en/ja の 2・3 行目を削除** します。レンダーが正常なのでマークアップ修正(M7)はこの表を見つけられません — 直すものがないと判断するのが正しいのです。つまり **文書は正常で、食い違っているのはパーサーだけ** です。

実例: `TOAST-DOCS/DDoS-Guard` `ko/l7-ddos-settings-guide.md` — 3 つの表が ko 1 行 / en・ja 10・9・3 行と読まれ、en 19 行・ja 16 行が削除待ちの状態です。

| 番号 | 項目 | 設定例 |
|---|---|---|
| 1 | ヘッダータイムアウト | client_header_timeout 10s<BR>client_body_timeout 10s |

<a id="table-parse-newline"></a>
## B. 実際の改行で途切れた表 { #table-parse-newline }

表の内容は A と同じで **区切り文字 1 文字だけが違います** — U+2028 ではなく **実際の `\n`** です。この場合はレンダーも一緒に壊れ — 続く行が表の外の段落として落ちます — マークアップ修正(M7)が「表セル内の改行で行が 2 つに割れた」として検出し、改行を 1 つ削除して直します。

つまり **A と B はパイプラインには同じ形で、文書整備には違う形** です。整備が在庫を減らしてくれるのは B だけで、A はレンダーが正常なため整備が原理的に届きません。

| 番号 | 項目 | 設定例 |
|---|---|---|
| 1 | ヘッダータイムアウト | client_header_timeout 10s<BR>client_body_timeout 10s |

<a id="table-parse-outlier"></a>
## C. パイプが 1 つ足りない行 { #table-parse-outlier }

3 言語とも **3 行 4 列で、行数もすでに一致しています。** ただし en/ja の 2 行目だけ区切りのパイプが 1 つ足りず 3 セルになっています。

表の列数を求める `_table_ncols` は行の **最小** セル数なので、この表の列数が 3 と読まれます。その結果 ko(4 列)とスキーマが違うと判定され — 実際は同じなのに — 最も破壊的な修復である **ヘッダーを含む表全体の書き直し** が選ばれます。行数はすでに一致しているので、「行数は文書整備が揃えてくれる」という前提では防げない箇所です。

実例: `OCR#177`(ビルド #370)— ko 10 行 / en 10 行なのに en の 3 行が 4 セルではなく 6・3・3 セルで、モデル呼び出し 4 回、en は検証 2 回失敗で未修復、ja は無意味な列同期。同じ形がコーパス全体で 13 文書に残っています(`Alimtalk/en/error-code.md` は 230 行の表)。

| 名前 | 種類 | 形式 | 説明 |
|---|---|---|---|
| tokenId | Header | String | トークン ID |
| appKey | Path | String | アプリキー |
| pageSize | Query | Integer | 1 ページの項目数 |

<a id="table-parse-control"></a>
## D. 対照群 — 本当に行が欠けた表 { #table-parse-control }

en/ja に ko の `SVC-104` 行がありません。よく整列した keyed 表なので、A・C のガードとは無関係に **依然として修復されるべき** です。この節がないと、「直さない方向にだけ安全になった」変更と区別がつきません。

| コード | 説明 |
|---|---|
| SVC-101 | リクエスト形式が正しくありません |
| SVC-102 | 認証情報がありません |
| SVC-103 | リクエスト上限を超えました |
| SVC-104 | 対象リソースが見つかりません |
