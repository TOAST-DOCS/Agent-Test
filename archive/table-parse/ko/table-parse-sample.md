## 표 파싱 샘플 { #table-parse-sample }

이 문서는 **표의 행 수를 누가 어떻게 세는가** 가 도구마다 갈리는 자리를 모아 둔 픽스처입니다.
사용자 가이드 메뉴(`ko/nav.yml`)에 등록하지 않습니다 — 배포되는 문서가 아니라 파이프라인 픽스처입니다.

한 표의 행 수를 세는 주체가 셋 있고, 셋이 같은 답을 내지 않습니다.

| 세는 주체 | 무엇으로 세나 | 무엇을 정하나 |
|---|---|---|
| 사이트 렌더러 | python-markdown — 줄바꿈은 `\n` 하나뿐 | 독자가 보는 행 수 |
| 번역 파이프라인 | `str.splitlines()` 로 자른 뒤 파이프로 시작하는 줄 | 표 수리의 판단 근거 |
| 마크업 정정(M7) | 렌더 결과가 원문보다 행이 많은가 | 정비가 고칠 수 있는 범위 |

아래 네 절이 그 어긋남의 네 모양입니다. 각 절의 기대 판정은 `scripts/check_table_parse.py` 가 결정적으로 검사합니다.

<a id="table-parse-u2028"></a>
## A. U+2028 로 끊긴 표 { #table-parse-u2028 }

첫 행의 마지막 셀에 **U+2028**(LINE SEPARATOR)이 들어 있습니다. 마크다운은 이 문자를 줄바꿈으로 보지 않으므로 **렌더된 표는 3행으로 멀쩡합니다.** 그런데 `str.splitlines()` 는 U+2028 을 줄바꿈으로 자르기 때문에, 파이프라인은 이 표를 **1행** 으로 읽습니다.

결과: 번역의 표 reconcile 이 "ko 는 1행인데 en/ja 는 3행" 으로 읽고, ko 를 정본으로 삼아 **en/ja 의 2·3행을 삭제** 합니다. 렌더가 멀쩡하므로 마크업 정정(M7)은 이 표를 보지 못합니다 — 고칠 것이 없다고 보는 것이 맞습니다. 즉 **문서는 정상이고 어긋난 것은 파서뿐** 입니다.

실사례: `TOAST-DOCS/DDoS-Guard` `ko/l7-ddos-settings-guide.md` — 표 3개가 ko 1행 / en·ja 10·9·3행으로 읽혀 en 19행 · ja 16행이 삭제 대기 상태입니다.

| 번호 | 항목 | 설정 예시 |
|---|---|---|
| 1 | 헤더 타임아웃 | client_header_timeout 10s client_body_timeout 10s |
| 2 | 유휴 연결 정리 | keepalive_timeout 15s |
| 3 | 재시도 제한 | proxy_next_upstream_tries 2 |

<a id="table-parse-newline"></a>
## B. 실제 줄바꿈으로 끊긴 표 { #table-parse-newline }

표의 내용은 A 와 같고 **구분 문자 한 글자만 다릅니다** — U+2028 대신 **실제 `\n`** 입니다. 이 경우에는 렌더도 함께 깨져서 — 이어지는 줄이 표 밖 문단으로 떨어집니다 — 마크업 정정(M7)이 "표 셀 안의 줄바꿈으로 행이 둘로 쪼개짐" 으로 적발하고 줄바꿈 하나를 지워 고칩니다.

그래서 **A 와 B 는 파이프라인에게는 같은 모양이고 문서 정비에게는 다른 모양** 입니다. 정비가 재고를 줄여 주는 쪽은 B 뿐이고, A 는 렌더가 멀쩡해서 정비가 원리상 닿지 않습니다.

| 번호 | 항목 | 설정 예시 |
|---|---|---|
| 1 | 헤더 타임아웃 | client_header_timeout 10s
client_body_timeout 10s |
| 2 | 유휴 연결 정리 | keepalive_timeout 15s |
| 3 | 재시도 제한 | proxy_next_upstream_tries 2 |

<a id="table-parse-outlier"></a>
## C. 파이프가 하나 빠진 행 { #table-parse-outlier }

세 언어 모두 **3행 4열이고 행 수도 이미 같습니다.** 다만 en/ja 의 두 번째 행만 구분 파이프가 하나 빠져 3셀입니다.

표의 열 수를 구하는 `_table_ncols` 는 행들의 **최소** 셀 수라, 이 표의 열 수가 3으로 읽힙니다. 그래서 ko(4열)와 스키마가 다르다고 판정되고 — 실제로는 같은데 — 가장 파괴적인 수리인 **header 포함 전체 재작성** 이 선정됩니다. 행 수가 이미 일치하므로 "행 수는 문서 정비가 맞춰 준다" 는 전제로는 막히지 않는 자리입니다.

실사례: `OCR#177`(빌드 #370) — ko 10행 / en 10행인데 en 세 행이 4셀 대신 6·3·3셀이라 모델 호출 4회, en 은 검증 2회 실패로 미수리, ja 는 무의미한 열 동기화. 코퍼스 전수로 같은 모양이 13개 문서에 남아 있습니다 (`Alimtalk/en/error-code.md` 는 230행짜리 표).

| 이름 | 종류 | 형식 | 설명 |
|---|---|---|---|
| tokenId | Header | String | 토큰 ID |
| appKey | Path | String | 앱키 |
| pageSize | Query | Integer | 한 페이지의 항목 수 |

<a id="table-parse-control"></a>
## D. 대조군 — 진짜로 행이 빠진 표 { #table-parse-control }

en/ja 에 ko 의 `SVC-104` 행이 없습니다. 잘 정렬된 keyed 표이므로 A·C 의 가드와 무관하게 **여전히 수리되어야** 합니다. 이 절이 없으면 "안 고치는 쪽으로만 안전해진" 변경과 구별되지 않습니다.

| 코드 | 설명 |
|---|---|
| SVC-101 | 요청 형식이 올바르지 않습니다 |
| SVC-102 | 인증 정보가 없습니다 |
| SVC-103 | 요청 한도를 초과했습니다 |
| SVC-104 | 대상 리소스를 찾을 수 없습니다 |
